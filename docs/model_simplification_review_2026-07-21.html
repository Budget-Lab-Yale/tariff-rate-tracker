Bottom line

I found no sign that the baseline results are broadly wrong. The main tests passed. The larger concern is future error: one policy fact can appear in several parts of the model, and several different routes can produce a public result. A change can therefore be correct in one place but quietly missing in another.
Work already completed. The project now finds every test file automatically. The daily summaries for countries and product groups use the same shared calculation instead of three copied versions. A new small saved example also checks that a baseline result and a “no §232” result are written correctly.

The main problem is not the number of tariff programs. The problem is that the model often describes the same program more than once: first when reading source material, again when preparing calculation inputs, again in the main calculator, and sometimes again for scenarios or daily reports. Each copy is understandable on its own. Keeping the copies in agreement is the dangerous part.

The clearest scenario risk has now been fixed. A scenario such as “no §232” now removes that program before calculation and rebuilds the result. Normal and scenario runs also use the same builder, so earlier interactions with other programs are recalculated instead of being left behind.
Current three-item priority order. (1) Run a full production parity checkpoint for the cleanup already completed. (2) Build the product-by-country table once and remove every program-specific row-building route. (3) Finish the common policy format, moving simpler authorities first and §232 last. Calendar and package-structure work are outside this work period.

Six recommendations, in priority order

1

Give every tariff program one official description.

Do not keep both the old and new descriptions alive indefinitely.
Risk reduction: very highPossible deletion: 2.5–4k linesEffort: high

The model is partway through a redesign. A newer, common format describes tariff programs, but important §232 details still live in an older bundle of data. Some information is copied into the new format while some remains in the old one. The main calculator reads both.

This forces a reviewer to remember which version controls each detail. It also means a future correction might update only one version.

Read the legal facts
products, countries, rates, dates
→
Create one policy description
including exceptions and interactions
→
Calculate once
then validate and publish

Recommendation: finish moving every live tariff program into the common format, then delete the older routes. Keep the actual policy logic in R code so it remains reviewable; do not replace it with a large, hard-to-audit settings language.

Status: implemented. Sentinel rate strings and the residual §232 payload are gone. §201, both §301 stacking flavors, metal derivatives, country deals, and every named §232 heading now reach the calculator as explicit programs. Validation rejects the deleted representation.

If the group cannot fund the full move, simplify the new layer and clearly document it as a wrapper. A smaller honest design is safer than two half-complete calculation systems.

2

Build the product-by-country table once.

Each tariff program should add only the rates and labels that it changes.
Risk reduction: highPossible deletion: 0.8–1.5k linesEffort: medium-high

Several programs separately add missing product-country rows, update rows that already exist, and fill unrelated tariff columns with zero. At the end, the model builds the complete table anyway.

This repetition makes every new program responsible for knowing the shape and default values of every older program. That is unnecessary coupling and an easy source of missing or stale columns.

  1. Create the complete product-country list once.
  2. Give each row a stable identifier.
  3. Let each tariff program return only the rows it changes.
  4. Combine the changes once, check the totals once, and publish once.

This keeps the current output shape and should not require more memory than the finished table already uses. It removes repeated row-building code and gives defaults one clear home.

Status: implemented. The Cartesian product is created once by build_rate_grid(). Program-specific row builders, densifiers, and the alternate resolved-program table/stacker were deleted; the final row-count and natural-key invariants are mandatory.

3

Use one calendar for every policy change.

A date should have one answer everywhere in the model.
Risk reduction: very highPossible deletion: 0.3–0.7k linesEffort: medium

Most mid-period policy changes cause the model to calculate a new dated snapshot. One Swiss expiration is handled differently: later reporting code edits the rate after the main calculation. The exception exists because the saved result does not retain enough information to rebuild the correct post-expiration rate.

Recommendation: save the underlying rate, the temporary floor, and their active dates. Then calculate every start or expiration date through the same route.

Status (22 July): still open — now the top-priority next step. The §122 expiration was already moved onto the calendar (the 2026-07-24 boundary snapshot now exists); Swiss is the last remaining exception.

What goes away
Special expiration edits in daily reports and point-in-time queries.
What improves
Published snapshots, daily reports, and one-date lookups all use the same policy state.
4

Recalculate scenarios from changed policy inputs.

Never create a scenario by editing finished rates.
Risk reduction: very highLess repeated codeStatus: completed

Previously, some scenarios calculated the baseline and then erased one tariff program’s final rate. That could leave behind effects the program had on other rules.

Status: completed in the current cleanup. A “no §232” scenario now removes §232 at the start and runs the normal calculation again. Normal and scenario runs use the same builder.

Exemptions, floors, trade preferences, and interactions with other programs can now adjust naturally. The calculator also stops with an error if a future scenario accidentally tries to skip this safer route.

5

Make dependencies clear and run every test.

A test that CI never runs provides false comfort.
Risk reduction: highPossible deletion: 0.3–0.7k linesEffort: medium

Before this cleanup, several files worked only when other files happened to be loaded first. The regular CI job also ran only a hand-picked subset of tests. A broader test run found stale assumptions and missing dependencies that the normal checks had missed.

Status: the immediate problem is fixed. CI discovers every test file, runs each separately, and clearly reports checks skipped because needed source material is absent. A small saved example now protects the shared baseline and scenario builder too.

Next step: give the model a formal internal package structure. Each file should state what it needs, and loading order should never decide whether a function exists.

6

Use one method for daily summaries.

Country and product-group reports repeat the same arithmetic.
Risk reduction: mediumLess repeated codeStatus: completed

The daily reporting file had separate but nearly identical calculations for countries and two kinds of product groups. It also prepared the same interval data several times.

Status: completed in the current cleanup. The data is now prepared once for each period, and the three grouped reports use the same summary method. The special breakdown by tariff program remains separate because it answers a different question.

This reduces the chance that one report quietly uses a different denominator or missing-data rule from the others. The full daily-report test suite passes.

How to know the cleanup is finished

A maintainer should be able to answer each of these questions from one place:

  • Which products, countries, dates, and rates define a tariff program?
  • How does that program interact with other tariffs and trade preferences?
  • What policy was active on a given date?
  • What input did a scenario change?
  • Which calculation produced a published number?

The goal is not merely fewer files. It is a clear, reviewable path from a legal fact to every published number.

How this review was done. I inventoried the repository, traced the main baseline and scenario calculations, reviewed the calendar and reporting paths, read prior architecture notes, checked file syntax, and ran the available tests. Estimates of possible code deletion are rough planning ranges, not promises.

Scope. This is a software-structure review, not a new legal review of every tariff action and not a full production-data rebuild. It identifies places where the software makes legal or numerical mistakes easier to introduce or harder to detect.
