Maintainability & policy-risk review

Make the model smaller by giving it one way to mean each thing.

A structural audit of the Tariff Rate Tracker, focused on reducing code volume without turning the model into an opaque configuration language—and on shrinking the surface area where a plausible-looking output can be wrong.

Review date: 21 July 2026 · Revision: 54b0fb9 (master) · Scope: production R model, scenarios, timeline, aggregation, and tests

Verdict Code shape Recommendations Migration order Safety evidence Quick wins

Bottom line

I did not find evidence that the current baseline is broadly broken. The core smoke suites completed with 202 passing assertions and no failures. But the codebase has a high structural risk: the same policy fact is often represented in several places, and the same output can be reached through distinct baseline, scenario, point-query, daily, and publishing paths. That creates opportunities for a change to land in one representation while silently missing another.
Implementation update, 21 July 2026. Recommendations 5 and 6 have begun: CI now discovers all 35 test entry points, hidden module dependencies and stale expectations were repaired, and the country/GTAP/HS daily rollups now share one aggregation kernel and one prepared interval context. The complete discovered suite passes; files containing internally skipped artifact checks are marked separately by the runner.

The model’s complexity is not mainly “too many tariff rules.” It is representation multiplicity: bespoke parser objects, an adapter, partially normalized specs, a residual §232 blob, a wide rate panel, a default-off long panel, repeated rate-column registries, synthetic boundary snapshots, and a downstream expiry mutation. Each layer is locally understandable; their coexistence is what makes the whole difficult to reason about.

The sharpest current example is scenario disabling. apply_authority_disables() zeroes authority columns late in the calculation. Its own documentation notes that earlier cross-authority interactions are not re-derived—for example, disabling §232 does not recompute earlier IEEPA floor logic. A “no §232” result can therefore be a late-edited baseline, not the result of calculating a world with no §232. This should be made impossible by construction.

Six recommendations, in priority order

1

Finish the authority abstraction—or remove it. Do not keep the halfway state.

Compile policy facts into one executable program representation, then let the calculator consume only that representation.
Risk reduction: very highNet deletion: 2.5–4k linesEffort: high

Why this is the largest simplification

AuthoritySpec promises one uniform authority shape, but the adapter still parks the 21-field §232 parser object at programs[[1]]$rate$resolved. The calculator immediately reconstructs s232_rates from it, while some rates, deals, gates, annex maps, exemptions, and stacking classes are also copied into normalized fields.

That means a reviewer must know which field is authoritative for each sub-rule. The adapter’s comments repeatedly describe “de-blob” migration planks; the production architecture should not permanently expose migration state as domain architecture.

Concrete evidence
  • build_authority_specs() is about 421 lines.
  • calculate_rates_for_revision() is about 2,321 lines.
  • §232 is read both through normalized program fields and through s232_rates_from_specs().
  • resolved_programs.R adds a second, default-off representation that expands to roughly seven times the panel rows.
  • stacking.R still carries a hand-maintained skeleton mapping rate columns back to spec authorities.

The target design

Parse legal facts
HTS entries, resource tables, rates, dates
→
Compile programs
scope + rate semantics + adjustments + precedence
→
Apply programs
one generic executor, then one stack and schema pass

Keep policy logic in code. This is not a recommendation to create a giant YAML DSL. Use small typed R constructors for scope, rate, floor, exemption, utilization, and stacking. Let specialized resolvers—especially the §232 annex classifier—produce those objects. Once compiled, no calculator function should read raw parser blobs or policy_params directly.

Deletion condition: when all live consumers use the compiled form, delete rate$resolved, s232_rates_from_specs(), the default-off resolved panel, duplicate stacking registries, and authority-specific “read it a second way” branches. If the team cannot fund that migration, the safer short-term choice is to roll AuthoritySpec back to a thin documented facade instead of maintaining two partial engines.

2

Allocate the product-country panel once; have authorities emit sparse patches.

Replace repeated “update existing rows, add missing pairs, fill every other authority with zero” code.
Risk reduction: highNet deletion: 0.8–1.5k linesEffort: medium-high

The calculator begins with only footnote-linked rows, then each blanket authority mutates existing rows and manufactures missing rows. §122, §201, §301, IEEPA, fentanyl, and §232 all contain variations on this shape. Finally, ensure_dense_grid() allocates every remaining MFN-only pair anyway.

The repetition is not harmless. Every new authority must know the current list of all other rate_* columns and their safe defaults. Scenario-only columns require special NA lifecycle comments and late deletion. This is why rate-column lists recur throughout schema, stacking, daily aggregation, validation, and calculator code.

Examples
  • add_blanket_pairs() and ensure_dense_grid()
  • Manual zero-filled row creation near §122 GN6, §301, IEEPA, and §232
  • SAFE_NA_COLUMNS in the 180-line densification helper
  • Repeated lists such as rate_232, rate_301, rate_301_cs, …

A memory-safe replacement

  1. Create the eventual dense pair table once, with a stable integer pair_id, base-rate columns, and canonical defaults. The model already reaches roughly 4.7 million rows per revision, so this does not enlarge the final object.
  2. Each compiled authority returns only non-zero or metadata-bearing patches: pair_id, authority_id, statutory_rate, effective_rate, tags.
  3. Apply patches by reference to wide output columns, or reduce patches to one wide block once. Do not retain a ten-authority long table for every pair; the existing prototype documents the 7× row penalty.
  4. Stack once, validate once, and write once.

This pattern centralizes defaults and pair creation while preserving the wide output contract and current performance strategy. A new authority supplies one patch producer and one registry entry; it no longer constructs rows containing zeros for every authority that already exists.

3

Make “state at date D” the only temporal operation.

Use one event calendar and synthetic snapshots; retire downstream policy mutation.
Risk reduction: very highNet deletion: 0.3–0.7k linesEffort: medium

The timeline is much better documented than most of the model, but it still has two state-change mechanisms:

  • discover_boundaries() and build_boundary_mints() recompute synthetic snapshots for most mid-revision changes.
  • apply_expiry_zeroing() mutates Swiss reciprocal rates downstream for daily aggregation and point queries. The daily pipeline must split intervals, zero a column, and re-stack.

The stated reason is revealing: a recompute after the Swiss framework expiry would restore an underlying pre-floor surcharge, but the snapshot does not store that underlying component, so downstream code conservatively forces the result to zero. The temporal exception is compensating for a missing policy-state representation.

Recommended change

Store the reciprocal layers needed to resolve the post-expiry state—e.g. underlying surcharge, framework floor, and their validity windows—in the compiled program state. Then every boundary, including Swiss expiry, can mint a snapshot by invoking the same calculate_at(date) operation. Point queries simply select the interval; daily aggregation simply broadcasts it.

Delete or collapse
collect_expiry_adjustments(), expiry_boundaries(), apply_expiry_zeroing(), apply_post_interval_adjustments_point(), expiry-specific branches in daily expansion, and the “mint versus zeroing” mutual-exclusion protocol.
Gain
The published snapshot panel, point query API, daily outputs, and downstream tariff model all read the same state. There is no class of policy change visible only to daily reports but absent from published snapshots.
4

Make scenarios inputs, never edits to resolved rates.

One revision builder for baseline and scenarios; scenario composition for shared definitions.
Risk reduction: very highNet deletion: 0.3–0.6k linesEffort: medium

There are currently two classes of scenario:

  1. Overlays that genuinely change inputs before resolution, such as USMCA utilization or metal-content assumptions.
  2. disabled_authorities, applied near the end of the calculator by zeroing output columns.

The second class must disappear. “No §232” should remove §232 programs before pair resolution, so floors, exemptions, stacking, statutory shadows, and USMCA interactions naturally recompute. A scenario should be equivalent to baseline plus a different set of compiled policy programs—not baseline output plus a patch.

Also route every scenario revision through build_revision_snapshot(). build_alternative_timeseries() currently repeats JSON loading, parsing, extraction, spec building, calculation, error handling, snapshot naming, and interval assembly. It even mutates an obsolete .pp value in the calculator’s environment despite the calculator now receiving policy_params explicitly.

Config composition should remove copied facts, not add a language. Let new_301 include the forced_labor overlay plus a Brazil program. Give list fields explicit merge semantics, especially boundary dates. Today both overlays repeat a 60-country roster and must re-list baseline boundary overrides because deep merge replaces lists wholesale; the comments correctly warn that omitting one can shift policy timing.

5

Turn src/ into an actual module boundary and discover every test automatically.

Eliminate hidden source-order dependencies and the false confidence of orphaned tests.
Risk reduction: highNet deletion: 0.3–0.7k linesEffort: medium

helpers.R sources nine modules and acts as a global symbol injector. Some files claim to be directly sourceable but call helpers they do not import. Other files use exists(), conditional source(), and environment mutation to compensate for uncertain load order.

In a targeted run of 12 standalone test files, 5 failed. Four failures were hidden dependencies—read_csv_cached() or ensure_cols() did not exist when a documented module was sourced directly. A fifth test asserted that the §122 expiry must not mint, contradicting the current timeline implementation and the passing mint-equivalence test. These are not numerical failures, but they show that tests outside the hand-picked CI list can rot unnoticed.

Status: the runner and immediate dependency repairs are implemented. All 35 discovered test files pass. Packaging src/ as a true namespace and adding a committed artifact fixture remain future work.

Recommended shape

  • Create a lightweight internal R package (it need not be published): R/, DESCRIPTION, NAMESPACE, and explicit imports. Keep CLI files in scripts/ as thin wrappers.
  • Move top-level executable code behind main(); never make function availability depend on source order.
  • Adopt one test runner that discovers every test-*.R, or maintain one explicit manifest checked against the filesystem. Mark artifact-required suites explicitly and make “skipped because snapshots are missing” visible as a separate CI status.
  • Make direct module tests source the package namespace, not a bespoke subset of files.

This change pays for itself during the larger refactor: it lets code move without preserving accidental globals, and it turns “what depends on this?” from a repository-wide grep into a namespace error.

6

Replace four daily rollups with one aggregation kernel.

Overall, country, GTAP, and HS-category outputs are variations of the same operation.
Risk reduction: mediumNet deletion: 0.3–0.6k linesEffort: medium

build_daily_aggregates() is about 575 lines and defines nested functions for overall, country, GTAP category, HS category, and authority decomposition. The country/category/HS functions repeat the same unweighted summaries, weighted numerator, denominator join, interval metadata, and empty-data behavior. Several paths also call prepare_interval_data_effective() repeatedly for the same interval.

Build one interval context once—effective panel, weighted panel, denominators, and classification columns—then pass dimension specifications to a single aggregate_dimension(context, keys, denominator). Keep authority decomposition as the one specialized reducer because its measures differ materially.

This is a relatively safe, parity-friendly project to do before the calculator rewrite. It reduces code and compute, and it gives streaming, monolithic, baseline, and scenario aggregation a single kernel to test.

Status: implemented as shared grouped unweighted and weighted kernels. Effective and raw panels are now prepared once per interval segment and reused by every rollup; authority decomposition remains specialized.

Migration order that keeps the numbers defensible

Phase 0

Seal the safety boundary

Make every test discoverable; repair the five standalone failures; add a small committed artifact fixture; require scenario invariants and snapshot/daily agreement.

Phase 1

Unify execution paths

One revision builder, one interval builder, one aggregation kernel. Delete obsolete environment mutation and the legacy scenario registry after parity.

Phase 2

Normalize pair construction

Allocate the dense panel once and introduce sparse authority patches behind the existing output schema.

Phase 3

Compile programs authority by authority

Migrate §122 and §201 first, then §301/IEEPA, then §232 last. At each step, remove the corresponding blob reads immediately.

Phase 4

Collapse time

Represent underlying Swiss state, mint every boundary, and remove all downstream expiry mutation.

Phase 5

Delete the scaffolding

Remove the default-off long engine, duplicate registries, adapter migration comments, retired flags, and parity shims. Re-measure the codebase.

A practical stopping rule

The refactor is done when a maintainer can answer these questions from one place each:

  • What products, countries, dates, and rates define an authority?
  • How does that authority interact with MFN, §232, preferences, and other authorities?
  • What exact state is in force on a date?
  • How does a scenario change those inputs?
  • Which calculation produced the published panel and every derived aggregate?

Today, several of those answers require tracing the adapter, calculator, config, resource loaders, stacking registry, timeline, and daily layer together. The goal is not merely fewer files. It is one executable chain of custody from legal fact to published cell.

Method. Repository-wide inventory and static dependency search; deep reading of the build orchestrator, parsers, AuthoritySpec/adapter, rate calculator, stacking engines, timeline, daily aggregation, scenario registry/configuration, output schema, architecture notes, and relevant historical reviews; syntax parsing; and targeted local tests. Estimates are directional net line reductions, not commitments. They assume parity shims are deleted after migration rather than retained indefinitely.

Important scope note. This is a structural simplification review, not a fresh legal audit of every tariff proclamation or a full production-data rebuild. It identifies where the software architecture makes legal and numerical mistakes more likely and how to shrink that surface.
